# Miss Log: Servo's learning half

## What this file is
The persistent error-sensing half of the task-completion system. Every time a delivered task misses (the user redirects, corrects, or rejects it), the miss is recorded here by category. Single misses get diagnosed and adjusted on the spot. Repeated misses in one category trigger a structural fix. The running count by category is the dashboard showing which stage of the system is leaking.

This file is Project Knowledge. Claude loads it on task-completion work, logs misses to it, and reads the tally to know where the system is weakest.

## The error taxonomy
A miss gets exactly one category, chosen by where the failure originated:

- TRIAGE: wrong size routing. Heavy process on a simple ask, or a thin answer to something that needed the full build.
- INTENT: decoded the wrong ask. Competent answer to an adjacent question.
- FORK: assumed when it should have asked, or asked when it should have assumed.
- SCOPE: defined "done" wrong, or missed a component that "done" required.
- ASSUMPTION: filled a gap with a wrong fact or wrong choice.
- BUILD: a component built wrong: unhappy path, unwired part, missing last mile.
- STALE: relied on a fact that was outdated or unverified.

## The record format
One row per miss in the log table below:
- Date: when.
- Task: one phrase naming the task.
- Category: one of the seven above.
- Miss: what was delivered versus what was wanted, one line.
- Root cause: which stage leaked, one line.
- Adjustment: the feed-back applied (spec update, calibration tweak, or checklist addition) and where it lands.

## How the loop closes
- Single miss: diagnose, log the row, apply the adjustment immediately.
- Pattern (3 or more in the same chain, per the Part 3B threshold): trigger a structural fix to the responsible rule or spec, not just a point fix. The threshold counts by chain, not by category label: three instances of one mechanism is a pattern, three instances sharing only a category name is not.
- Recurrence: a new miss in a chain that already received a structural fix is a recurrence, not a fresh single miss. The prior fix did not hold. Re-trigger escalation on the first recurrence (do not wait for three more), reopen and replace the failed fix via Part 3 / Part 3D rather than point-patching it again, and mark the chain [REGRESSED] in the dashboard until the replacement fix is verified. Marking [REGRESSED] also opens an OWED-FIX entry in the dashboard (see below). Every recurrence feeds the recurrence-rate metric below. A miss in a different chain of the same category is not a recurrence, however the category tally reads.
- Breached working adjustment: a point fix or recorded working adjustment that is breached on its first application escalates immediately, regardless of count. An adjustment that does not survive its own first test is a recorded intention, not a fix, and restating it is the deflection Part 3 names. Mark the chain [ESCALATED] and open an owed-fix entry; the replacement must be a mechanism verified by something other than its author, not another intention. This is the third escalation trigger, alongside the three-strike threshold and the recurrence sub-clause, and it is the one that fires below three.
- Dashboard: the tally below. The stage to fix next is the chain with the largest count and an open debt, not the category with the largest total: a category can lead the tally entirely on closed chains while a smaller chain carries the live leak. Read the chain lines and the owed-fix list together; the category totals are for arithmetic, not for triage.

## Category tally (the dashboard)
Each non-zero chain carries a fix-status bracket, and a category with a single chain carries it at the category line: [OPEN] = misses logged, below threshold, point-fixed only; [FIXED] = reached the three-strike threshold and received a structural fix; [REGRESSED] = a new miss landed after that structural fix (a recurrence; the fix did not hold); [ESCALATED] = a structural fix is owed and has not been authored, whether triggered early by a breached working adjustment or by the three-strike count, and the chain has not since regressed against a shipped fix. Zero-count categories carry no bracket.

Every chain marked [REGRESSED] or [ESCALATED] carries an open OWED-FIX entry in the list below. A [REGRESSED] entry names the structural fix that failed and every date it was breached; an [ESCALATED] entry names the working adjustment that was breached, or the three-strike count reached, and the fix not yet authored. The entry is a debt, not a note: it clears only when a replacement structural fix is recorded against it, never merely because a new row was appended to the log or a point fix was applied to the latest instance. Appending a row updates the breach dates on the existing entry; it does not close it. An [OWED-FIX] left open across multiple breach dates is itself the signal that the chain needs rework at the rule or spec level rather than another point patch.

Chains: a category is a label, not a mechanism, and one category can hold more than one failure mechanism. Fix-status brackets and owed-fix entries attach to a *chain* (instances that share a mechanism), never to the category label alone. The operational test for whether two instances belong to the same chain: would one structural fix plausibly have prevented both? If not, they are separate chains and must be counted separately, because pooling them inflates the recurrence rate with breaches of a fix that never covered the later instance. A category with multiple chains shows its total count in the tally and its per-chain status beneath. Every chain assessment must also state what evidence would have kept the instances pooled; a split that cannot answer that is reasoning backwards from the count. Splitting is never itself a fix: it reassigns brackets and counts, it lowers the recurrence rate by definitional means, and it clears no debt. Parent-total invariant: a category's total must equal the sum of its chain counts. Any edit changing a chain count changes the parent in the same edit, and the equality is checked by someone other than the author of the edit before the commit lands. Log reconciliation: each category's tally total must also equal the number of dated log rows carrying that category. The parent-total invariant proves the tally is internally consistent; this one proves it still matches the record it summarizes, which a tally can drift from while remaining internally sound. Both invariants are arithmetic rather than editorial precisely because the author-side sweep they replace failed three consecutive times, twice on adjacent lines. Neither reaches prose: a renamed term left standing in the rule that instructs its use is invisible to both, and that subclass is what S2's owed structural fix still has to address.
